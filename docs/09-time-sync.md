# 09 · 时间同步

> 建图飘、点云糊、RViz 报 `Message Filter dropping message`，八成是时间问题。
> 这篇讲清楚为什么、以及有线模式下怎么用最小代价解决。

---

## 1. 为什么建图对时间这么敏感

FAST-LIO2 每来一帧点云，要做三件事：

1. 按每个点的采集时刻，用 IMU 积分把点"退畸变"回帧起始时刻
2. 用 IMU 预积分结果做帧间位姿预测
3. 把点配准到局部地图上

第 1、2 步都依赖**点云时间戳和 IMU 时间戳落在同一条时间轴上**。两端时钟差多少，
就相当于给每个点注入多少量的运动畸变。

| 时钟偏差 | 实际后果 |
|---|---|
| < 5 ms | 无感，正常 |
| 10–50 ms | 快速转向时点云轻微拖影，静止时看不出来 |
| 100–500 ms | 转弯时点云明显撕裂，LIO 残差上升 |
| > 1 s | 直接发散，RViz 里地图炸成一团 |

另外还有一层与建图无关、但一样致命的影响：**RViz 的 TF 有有效期**。
PC 的当前时间与消息时间戳差太多，TF 就被判为过期，
`Message Filter dropping message` 刷屏，画面定住不动。

## 2. 问题从哪来：Orin Nano 没有 RTC 电池

Jetson Orin Nano 载板上没有后备电池。断电之后：

- 时钟回落到镜像构建时刻
- 实测偏差可以到 **几百天**
- 上电后没有任何东西会纠正它（狗端无外网，`systemd-timesyncd` 是空转）

所以每次断电重启，狗端时间都是错的，且错得很随机。

FLMap.2 时代这个问题已经用 `go2-clock` 系列服务解决过；FLMap.3 把它收进仓库，
作为标准组件 —— 因为**有线让这件事变得更便宜**。

## 3. 有线带来的机会

| | Wi-Fi（FLMap.2） | 有线（FLMap.3） |
|---|---|---|
| 到 PC 的 RTT | 2–40 ms（省电模式可到 90 ms） | **0.55 ms** |
| 抖动 | 0.1–35 ms 随机 | **0.12 ms** |
| 单次校时误差 | 受 RTT 抖动影响，约 ±10 ms | **< 1 ms** |

RTT 越小、越稳，`服务器时间 + RTT/2` 这个单程补偿就越准。
0.55 ms 的对称链路上，单次采样误差已经小于 1 ms，**不需要 NTP 那种长期滤波**。

## 4. 方案：PC 授时，狗定时拉取

```
   ┌──────────────── PC ────────────────┐        ┌──── Go2 拓展坞 ────┐
   │                                     │        │                    │
   │  systemd-timesyncd                  │        │  go2-clock-pull    │
   │   （已同步外网 NTP）                 │        │   .timer 每 30 s   │
   │        │                            │        │        │           │
   │        ▼                            │  有线   │        ▼           │
   │  go2_timeserver.py :8000  ◀─────────┼─0.55ms─┼──  GET /time       │
   │   返回 %.9f epoch                   │        │  取最小 RTT 的样本  │
   │                                     │        │  clock_settime     │
   └─────────────────────────────────────┘        └────────────────────┘
```

选 HTTP 而不是标准 NTP，理由很实在：

- **不需要 root**。PC 侧绑 8000 端口是普通用户就能做的，NTP 要占 123 端口
- 协议开销完全可忽略（0.5 ms 链路上，HTTP 头那几十字节不算什么）
- 狗端 `ntpdate` 不支持自定义端口，而 HTTP 天然可以换端口

精度上换来的差别：HTTP 方案约 1 ms，NTP 约 0.1 ms。**对建图没有区别。**

## 5. 用法

### 5.1 PC 侧

```bash
./scripts/clock_sync.sh start     # 起授时服务（后台，日志 /tmp/go2_timeserver.log）
./scripts/clock_sync.sh check     # 只读：看狗端当前时间与偏差
./scripts/clock_sync.sh stop      # 停掉
```

### 5.2 狗端（只需装一次）

```bash
# 从 PC 推过去并安装（会用到狗端 sudo 密码）
./scripts/clock_sync.sh install
```

装上之后是四个 systemd 单元：

| 单元 | 作用 |
|---|---|
| `go2-clock-restore.service` | 开机先把时钟恢复到"上次已知时间"，避免 384 天的荒唐差值 |
| `go2-clock-pull.timer` | 每 30 s 向 PC 拉一次，开机 15 s 后首次 |
| `go2-clock-save.timer` | 每 60 s 把当前 epoch 落盘 |
| 对应 `*.service` | 上面三个的执行体 |

另外会**关掉 `systemd-timesyncd`** —— 狗端无外网，它只会反复失败并误导排查。

### 5.3 手动校时（调试用）

```bash
# 狗端
sudo go2-clock pull       # 拉一次并设钟
go2-clock status          # 看状态、看与 PC 的实时偏差
```

## 6. 实测

2026-10-19，千兆交换机，PC↔狗：

```
[go2-clock] PC=1792381938.741876  本地=1792381936.4xxx  偏差=-0.0049s  RTT=1.5ms
```

- **RTT 1.5 ms**（首次 HTTP 建连，之后复用连接约 0.6 ms）
- **残差 −4.9 ms**，在默认阈值 `GO2_STEP_THRESHOLD=0.010`（10 ms）内，
  因此脚本判定"无需改钟" —— 这是刻意的：**避免频繁步进导致 rosbag 时间倒流**。

想更严，改阈值：

```bash
# 狗端
sudo GO2_STEP_THRESHOLD=0.002 go2-clock pull
# 或写进 /etc/default/go2-clock 永久生效
```

> **注意方向**：`偏差 = 本地 − PC`。负数表示狗慢了。脚本会自动判断正负。

## 7. 还有一个容易忽略的：雷达时间戳

`livox_ros_driver2` 打时间戳有两种来源：

| 模式 | 行为 | 适合谁 |
|---|---|---|
| 用雷达内部时钟 | 时间戳来自雷达自己的晶振 | 只录包、事后回放 |
| 用主机时钟（默认） | 驱动收到包时打主机时间 | **实时建图，就是本方案** |

Mid360 还支持 PTP / GPS / PPS 授时（`timestamp_type` 参数），一旦正确接入，
雷达时间与主机时间会严格锁定。**但本方案不需要** —— 狗端时钟已经和 PC 对齐，
驱动用主机时间打戳，点云和 IMU 天然同源，这条链就闭合了。

如果哪天要接 PTP，前提是交换机支持 PTP（普通家用交换机不支持），
而且要给狗端配 `ptp4l`。对室内建图来说这是过度设计。

## 8. 验证与排障

### 8.1 三步确认时间没问题

```bash
# ① PC 授时服务在跑
curl -s --noproxy '*' http://192.168.123.10:8000/time; echo

# ② 狗端能拉到，且偏差小
ssh go2 'go2-clock status'

# ③ 两端 date 对得上（肉眼比对到秒即可）
date; ssh go2 date
```

### 8.2 症状表

| 症状 | 原因 | 处置 |
|---|---|---|
| RViz 画面定住，日志刷 `Message Filter dropping` | 狗端时钟前/后跳了太多 | `go2-clock status` 看偏差；>100 ms 就 `sudo go2-clock pull` |
| 狗端时间显示 2023 年或更早 | 断电后没恢复，pull 又没跑成 | 确认 `go2-clock-pull.timer` 是 active；确认 PC 授时服务在跑 |
| `go2-clock pull` 报 RTT 超过阈值 | 采样期间时钟自己跳了（刚开机常见） | 再跑一次，脚本内部已经重试一次 |
| 偏差一直在 10 ms 左右不动 | 阈值就是 10 ms，脚本判定"无需改" | 正常，不需要管；要更严就调 `GO2_STEP_THRESHOLD` |
| PC 端 `curl` 通、狗端 `curl` 不通 | ufw / 防火墙 | `sudo ufw allow 8000/tcp` |
| 校时后 rosbag 时间倒流 | 步进改钟 | 这是步进校时的固有代价；录包前先校时，录包中别再校 |

### 8.3 为什么不干脆用 chrony

可以，但没必要：

- 狗端没有外网，`apt install chrony` 走不通（实测过）
- chrony 的价值在于"长期滤波、驯服晶振漂移"。而这里**每次开机都是从零开始**，
  30 s 一次步进校准已经足够，不存在需要驯服的长期漂移
- 多一个后台守护进程，就多一个会静默失败的东西
