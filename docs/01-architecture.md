# 01 · 架构设计

> 这份文档回答三个问题：**为什么要把建图和可视化拆开？** 拆开之后 **数据怎么流？**
> 每个设计选择 **放弃了什么、换来了什么？**

---

## 1. 问题定义

原有的 FLMap 架构是「雷达 → PC → 建图 → RViz」：

```
Mid360 ──网线──▶ PC ──▶ livox_ros_driver2 ──▶ FAST-LIO2 ──▶ RViz2
```

在四足平台上，它有三条硬约束同时失效：

| 约束 | 具体表现 |
|---|---|
| **物理接口** | 狗身上只有一个空闲网口，雷达插上就没有 PC 的位置 |
| **操作距离** | 有线连接意味着操作者必须跟着狗走，机器狗的机动性被抵消 |
| **链路容量** | 原始配准点云 48 B/点 × 20 k 点/帧 × 10 Hz ≈ **77 Mbit/s**，Wi-Fi 顶不住 |

第三条最容易被低估。很多人以为「Wi-Fi 有 300 Mbps 啊」——那是物理层峰值，
真实单流吞吐在共享信道下通常只有 30–80 Mbps，并且丢一个 UDP 分片就要重传整条消息。

---

## 2. 三种可选架构

| 方案 | 建图在哪 | 数据过网 | 优点 | 致命问题 |
|---|---|---|---|---|
| A. 全部在 PC | PC | 原始点云（77 Mbit/s）+ IMU | 改动最小，直接复用原仓库 | 必须拖网线；Wi-Fi 下必挂 |
| B. 全部在狗上 | 狗 | 无 | 完全自主 | 看不到实时画面，只能事后拷 PCD |
| **C. 拆分（本方案）** | **狗** | **瘦身后点云（1.3 Mbit/s）** | **无线、实时、带宽可控** | 需要多一个桥接节点与 PC 端累加器 |

方案 C 的关键不是"把 RViz 挪到 PC"，而是**在链路上只传必要信息**。
一旦接受"狗端只发当前帧、PC 端自己攒图"，带宽就从 77 Mbit/s 掉到 1.3 Mbit/s，
降了两个数量级 —— 这才是无线方案能成立的原因。

## 3. 数据流与话题契约

### 3.1 完整链路

```
                    ┌───────────── 狗端（Orin Nano, Foxy）─────────────┐
Mid360              │                                                   │
  │ UDP 3.6 MB/s    │  livox_ros_driver2                                │
  └────────────────▶│    ├─ /livox/lidar   CustomMsg  20k 点 / 10 Hz    │
                    │    └─ /livox/imu     Imu       200 Hz             │
                    │              │                                    │
                    │              ▼                                    │
                    │        FAST-LIO2 (fastlio2_mapping)               │
                    │              ├─ /cloud_registered  PointXYZINormal│
                    │              │                    48 B/点, 10 Hz  │
                    │              ├─ /aft_mapped_to_init  Odometry     │
                    │              └─ /path               Path          │
                    │              │                                    │
                    │              ▼                                    │
                    │        flmap_bridge  ★                            │
                    │          体素 0.20 m → 重打包 xyz+i → 限流 5 Hz   │
                    └──────────────┬────────────────────────────────────┘
                                   │  /flmap/cloud   16 B/点, 5 Hz, 33 kB/帧
                        Wi-Fi ◀────┘        约 1.3 Mbit/s
                                   │
                    ┌──────────────▼───────────── PC 端（Humble）────────┐
                    │  flmap_accumulator  ★                             │
                    │    追加到本地缓冲 → 1 Hz 重发 /flmap/map           │
                    │              │                                    │
                    │              ▼                                    │
                    │           RViz2                                   │
                    └───────────────────────────────────────────────────┘
```

★ = 本仓库新增。

### 3.2 话题契约

| 话题 | 类型 | 发布者 | 频率 | 单帧大小 | QoS | 是否过网 |
|---|---|---|---|---|---|---|
| `/livox/lidar` | `livox_ros_driver2/CustomMsg` | 驱动 | 10 Hz | ~1.4 MB | RELIABLE | ❌ 仅本机 |
| `/livox/imu` | `sensor_msgs/Imu` | 驱动 | 200 Hz | ~300 B | RELIABLE | ❌ 仅本机 |
| `/cloud_registered` | `PointCloud2` (48 B/点) | FAST-LIO2 | 10 Hz | ~960 kB | RELIABLE | ❌ 仅本机 |
| **`/flmap/cloud`** | `PointCloud2` (16 B/点) | flmap_bridge | 5 Hz | **~33 kB** | RELIABLE（可调） | ✅ |
| `/aft_mapped_to_init` | `nav_msgs/Odometry` | FAST-LIO2 | 10 Hz | ~400 B | RELIABLE | ✅（极小） |
| `/path` | `nav_msgs/Path` | FAST-LIO2 | 1 Hz | 随轨迹增长 | RELIABLE | ✅（可选） |
| **`/flmap/map`** | `PointCloud2` (16 B/点) | flmap_accumulator | 1 Hz | 持续增长 | RELIABLE | ❌ 仅 PC 本地 |

> **`/livox/*` 和 `/cloud_registered` 不会跑到 Wi-Fi 上。**
> DDS 是按订阅关系推送的：PC 上没有节点订阅这两个话题，狗端就不会往外发。
> 所以不需要任何"话题白名单"机制 —— 这是 DDS 的天然行为，也是为什么本方案
> 不用做流量整形就能把 77 Mbit/s 挡在链路上。

## 4. 带宽账

```
每帧字节数 = 点数 × 每点字节数
链路带宽   = 每帧字节数 × 发送频率 × 8   (bit/s)
```

同样一套削减手段，FLMap.2 是为了"塞进 Wi-Fi"，FLMap.3 是为了"留出余量"：

| 阶段 | 点数 | 字节/点 | 频率 | 结果 | 说明 |
|---|---|---|---|---|---|
| 桥接前 `/cloud_registered` | 20 000 | 48 | 10 Hz | 76.8 Mbit/s | LIO 原始输出 |
| 桥接后（FLMap.2，Wi-Fi） | 2 061 | 16 | 5 Hz | 1.32 Mbit/s | voxel 0.20 |
| 桥接后（FLMap.3，有线） | ~9 100 | 16 | 10 Hz | **11.6 Mbit/s**（实测） | voxel 0.10 |

关键的对比不是"从 76.8 降到 10"，而是**这 10 Mbit/s 只占千兆链路的 1%**，
而且 FLMap.3 拿到的保真度是 FLMap.2 的四倍、帧率是两倍。

三处削减的贡献：

1. **重打包 48 → 16 B/点（×0.33）**：`PointXYZINormal` 里的法向量、曲率、
   以及 4 字节对齐填充对可视化完全无用。
2. **体素降采样（×0.40）**：`0.10 m` 体素保留墙面纹理和家具边缘；FLMap.2 用的
   `0.20 m` 会把同一块墙面上的上千个点压成一个质心，远看还行，近看发糊。
3. **限流（×1.0）**：有线不需要限流，10 Hz 直接跟 LIO 同频。FLMap.2 的 5 Hz 是
   为了省带宽加的。

> 那为什么还要 bridge，不直接把 `76.8 Mbit/s` 的原始点云发过去？千兆扛得住，
> 但 PC 端累加器的内存和 CPU 开销会翻 2.5 倍（每点 48 B 而不是 16 B），
> 而丢掉的法向量本来也不用于显示。**该省的地方省，不该省的地方不省。**
>
> 想试直通：`ros2 run flmap_bridge flmap_bridge_node --ros-args -p voxel_leaf:=0.02`
> 或者干脆让 RViz 直接订阅 `/cloud_registered`。

## 5. 关键设计决策

### 决策 1：狗端只发「当前帧」，不发「地图」

**放弃**：PC 端一接入就能看到完整历史地图。
**换来**：带宽与建图时长完全解耦 —— 走一小时和走一分钟，链路负载一样。

如果反过来（发地图），地图会随时间线性增长到几十 MB/帧，几小时后链路必然崩。
本仓库的选择是让 PC 自己累积：`flmap_accumulator` 每收到一帧就追加到本地缓冲，
1 Hz 重发一次完整累积结果给 RViz。地图再大也不消耗网络，只消耗 PC 内存
（默认上限 200 万点 ≈ 32 MB）。

### 决策 2：桥接节点用 C++ 且不依赖 PCL

狗端是 Orin Nano，6 核 A78AE 且被 FAST-LIO2 占掉大半。桥接节点每帧要遍历 20 000 点
做哈希体素化，Python 版本实测每帧 69 ms（会直接拖垮 10 Hz 的 LIO），
C++ 版本约 1–2 ms。所以桥接必须是 C++。

同时刻意**不引入 PCL**：PCL 的 `VoxelGrid` 会额外拷贝整份点云，
而且 Foxy 的 PCL 1.10 与 Humble 的 1.12 在 CMake 依赖传递上有差异。
本节点只用 `rclcpp` + `sensor_msgs` + `std::unordered_map`，两端都能无痛编译。

### 决策 3：全链路 RELIABLE，不做 QoS 降级

**最初的设想是错的，这里记录实测结论。**

设计阶段我打算让链路走 `BEST_EFFORT`：丢一帧只是画面晚 200 ms，而重传会堵住后面的帧。
实测（CycloneDDS 0.10 / Humble）发现：

```
发布端 RELIABLE  +  订阅端 BEST_EFFORT   ->   订阅端收到 0 帧
```

不是"降级接收"，而是**压根不建立匹配**。这意味着两个坑：

1. FAST-LIO2 的 `/cloud_registered` 默认是 RELIABLE，桥接若用 BEST_EFFORT 订阅，
   在真机上会**一帧都收不到**（本仓库开发过程中真的踩到了，合成源当时也是 BEST_EFFORT，
   所以本地测试掩盖了问题）。
2. RViz2 的 PointCloud2 显示项默认按 RELIABLE 订阅，桥接若用 BEST_EFFORT 发布，
   RViz 里就是一片空白 —— 而新手根本不会想到去改 QoS。

所以最终方案是**两端都 RELIABLE**，并且 QoS 做成参数
（`input_reliability` / `output_reliability`）：

- 33 kB/帧、5 Hz 的重传代价只有几毫秒的空口时间，远小于"看不见图"的排查成本
- 严格匹配，RViz 开箱即用，不需要用户改任何设置
- 链路极差时（比如 2.4 GHz 拥挤信道）再把两侧一起改成 `best_effort`，
  同时把 RViz 显示项的 `Reliability Policy` 改成 `Best effort` —— 文档里写清了成对修改

> **教训**：DDS 的 QoS 是"成对匹配"语义，不是"自动降级"语义。
> 任何一端改 QoS，另一端必须跟着改，否则表现为"话题在、数据没"。

### 决策 4：限流带 15% 容差

最初实现是「距上次发布 ≥ 200 ms 才发」。实测发现问题：真实输入帧间隔并不均匀
（0.05–0.36 s 抖动），严格判定会把大量帧丢掉 —— 目标 5 Hz 时实际只有 **2.9 H**z。

改成「≥ 170 ms 即发」（`rate_tolerance=0.85`）后，等价于一个带信用额度的限流器，
输出能贴着目标频率走：实测输入 9.71 Hz → 输出 **4.999 Hz**。
这个参数在 `src/flmap_bridge/config/bridge_default.yaml` 里可调，设 1.0 即恢复严格模式。

### 决策 5：PC 端不做逐帧去重

**放弃**：走回头路时不重复累积。
**换来**：每帧开销是 O(1) 的内存写入，而不是 O(n log n) 的集合运算。

因为每帧本身已经是 0.2 m 体素化的结果，重复点只出现在狗走回原地时，视觉上几乎看不出。
只有当缓冲达到 `max_points` 上限时，才做一次全局 `np.unique` 去重把内存压回去。

## 6. 失败模式与对策

| 失败模式 | 现象 | 设计上的对策 |
|---|---|---|
| Wi-Fi 丢包 | 画面卡顿、点云缺块 | BEST_EFFORT + 5 Hz，丢一帧只影响 200 ms |
| 链路带宽骤降 | 帧率掉到 1–2 Hz | `voxel_leaf` / `max_rate_hz` 运行时可调，见 05 文档 |
| 狗端 CPU 打满 | LIO 帧率下降、点云拖影 | 桥接 1–2 ms/帧；LIO 用 `taskset` 绑核，见 03 文档 |
| 数据流断档 | 点云突然朝一个方向飞走 | FAST-LIO2 的 gap-fix 补丁，见 07 文档 |
| 两端时间不同步 | RViz 提示 `message is too old` | 狗端无 RTC，需先校时，见 03 文档 §7 |
| DDS 发现失败 | `ros2 topic list` 看不到对方 | 四层体检脚本 + 单播配置，见 02 文档 |

## 7. 如果还要再改

几个自然的延伸方向，以及为什么本仓库没有直接做：

- **发 PCD 而不是发帧**：PC 端能拿到权威地图，但只能等扫描结束，失去实时性。
  真要的话，在狗端 `stop` 后用 `rsync` 把 `map.pcd` 拉回来即可（百兆级，几秒钟）。
- **用 Web 前端替代 RViz**：`foxglove_bridge` 能让浏览器看图，跨平台更友好；
  但 Foxglove 在 Foxy 上没有官方二进制，需要自己编译，故未纳入。
- **多狗/多机协同**：把 `ROS_DOMAIN_ID` 按机器编号，PC 端起多个累加器实例即可，
  架构本身不需要改。
